FlyRank Ranking Analysis Capstone

This page summarizes the capstone analysis from the notebook and is designed to be published as a static GitHub Pages site.

Abstract

This work studies which pages look most likely to be declining with visible demand and should be reviewed for refresh. Using a client-holdout evaluation on the anonymized starter dataset, a simple logistic model outperformed a transparent baseline rule on the same split, supporting editor triage rather than claiming a causal effect.

Problem

The decision supported here is whether a content editor should review a page for refresh. The ranking output is meant to focus attention on the highest-value review candidates, not to prove that any one intervention will improve outcomes.

Data

The analysis used the anonymized starter dataset and scored pages with positive impressions and content age of at least 90 days. The target was a directional label derived from trend direction, and the page text, titles, URLs, and client-identifying fields were not used.

Methodology

The baseline was a transparent refresh score based on visibility, freshness risk, and position opportunity. The model used a logistic regression trained on a client holdout split. The evaluation metrics below are reported on the same held-out split.

The learned model improved ranking quality on the same holdout split, with a higher ROC AUC and F1 than the transparent baseline.

Limitations

  • The target uses trend direction as a proxy for decline rather than a verified business outcome.
  • The analysis uses only pages with positive impressions and content age of at least 90 days.
  • The client holdout is a pragmatic estimate of future generalization rather than a guarantee of live performance.

Recommendations

Editors should use the ranked queue as a decision-support tool for review and refresh planning. The model is most useful for prioritizing human review, not for making automated claims about business impact.

Reproducibility

The analysis is implemented in the capstone notebook in the repository, and the exported metrics are stored in the outputs folder for inspection.
